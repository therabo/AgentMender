Status: IN PROGRESS. Updated 2026-11-01 (Europe/Rome). Review base is `c9dd04d` plus the in-progress M8.2 working tree. This is a read-only implementation review except for this review record; no provider process or real-user mutation has been invoked.

## Early boundary decision

Reviewed official Codex 0.166.0 source at commit `6ff1e1ca3b30fc8b914720681fcf5fe62e95f856` in an isolated source checkout. The scoped claim can be the selected root's exact Legacy/plain primary rollout and canonical `state_5.sqlite` row absent at the fenced cutoff. It must not become a claim that every possible external historical copy is absent.

The source independently supports the Legacy functional boundary:

- `codex-rs/thread-store/src/local/mod.rs:429` routes `load_history` to a live-writer rollout path or `read_thread` with history requested.
- `codex-rs/thread-store/src/local/read_thread.rs:69` only accepts SQLite for history when the rollout exists and its session metadata matches the requested thread. Lines 139-152 implement that check. Lines 287-352 read history from the rollout, rather than from projection rows.
- `codex-rs/thread-store/src/local/model_context.rs:35` resolves the selected existing rollout. Lines 55-84 read session metadata, check thread identity, and use full rollout history for Legacy. Paginated context uses a separately resolved lineage.
- `codex-rs/thread-store/src/local/thread_rollout_resolver.rs:83` requires an existing rollout even when metadata identifies a path. Missing Legacy paths fall back to root-local active/archived rollout discovery; missing Paginated paths do not.
- `codex-rs/thread-store/src/local/thread_history/read.rs:200` checks state metadata before projection reads and rejects Legacy at lines 227-229.
- `codex-rs/thread-store/src/local/live_writer.rs:436` writes Legacy directly to the rollout; projection is used in the Paginated branch.

An unknown external projection containing old content is therefore not independently sufficient for ordinary intact Legacy resume. It may remain a disclosed Unknown/Unsupported residual. Requiring proof of no external historical projection anywhere would exceed the accepted scoped objective. A known selected external `sqlite_home` is materially different: the root-local row cannot be represented as the provider's selected authoritative metadata while known configuration selects another state DB. Such known configuration must block this first profile before effects and be checked again under the fence.

## Handoff findings and architecture judgment

Review checkpoint concluded 2026-11-01; implementation acceptance is **PENDING**, not PASS. No concrete cross-session deletion or receipt-authority bypass was identified in the reviewed fixed SQL, lock ordering, WAL exclusion, fresh dedicated-port replan, or immutable report recording. That statement is limited to the working-tree snapshot; the following changes still require final review and evidence:

1. **Historical target producer admission:** enforce exact target row `cli_version` as well as exact target first-header `cli_version` both at observation and inside the actual database/file fences. The initial positive fixture omitted the row producer and must be updated. Provider owner has this finding.
2. **Current admission guard:** review newly added `scoped_config.rs` at the complete validation boundary, including a positive empty/default case and root/profile/project/environment rejection cases. The draft checks observed root file absence, selected environment values, system file absence and target cwd ancestry. It does not prove effective MDM/cloud/historical-process configuration; the accepted contract must explicitly remain declared-root bounded. Permission uncertainty must refuse. Recheck after fence acquisition and immediately before unlink.
3. **Approval disclosure:** before the existing terminal challenge, show scoped irreversibility/no transcript backup, exact session/root and primary actions, logical planned bytes, optional actions, and retained residual categories. Complete serialized metadata alone is a poor substitute for this required disclosure. Workflow owner has this finding.
4. **Domain/adapter ownership:** the current domain constants and validation know provider filenames (`state_5.sqlite`), six table names, rollout filenames, exact executable/schema hashes and version. This violates the repository's established adapter boundary and source fitness check. Do not waive the check. Move exact provider interpretation and admitted constants into the Codex adapter. Domain keeps pure categorical manifest identity, bounded unique row-set identifiers (or semantic roles), safe root-relative shapes, physical disjointness, subset/accounting/report laws, and binding of all supplied profile evidence. A semantic `CodexLegacyPlainV1` admission marker is acceptable; it must not cause the domain to interpret storage spellings. The independent provider preflight/fenced checks must still enforce exact profile and table closure for a forged-but-syntactically-valid manifest. Record this ownership in ADR-0017 before refactoring. This recommendation follows the software-architect skill and existing AGENTS/domain boundary, not a new approval flow.
5. **Production-path isolated acceptance:** the synthetic private test exercises real disposable SQLite/files, application planning, persistence, approval test gate, durable intent, reopen and refusal to execute twice. It bypasses executable identity and protected worker via private `cfg(test)` facilities. Add an opt-in ignored test using the real pinned official binary only for read-only identity hashing, an actual current CLI helper for the OS-denied protected worker, manually seeded disposable exact schema/metadata and the production adapter. Do not start the native provider, accept runtime synthetic pins in production, or touch real sessions. Final workspace gates and exact-commit OS CI remain parent release gates.

Native source check also confirms the writer fence's coordination model: `WriterLockCoordinator::acquire` obtains coordination before opening/locking a writer; `try_acquire_for_publication` holds coordination through publication, and stale-lock removal holds the same coordination. Existing live writers retain their writer locks until all file work ends. The cleanup fence's refusal unless **all** extant locks are idle is therefore necessary; checking only the target would not protect newly published references. The maintenance lock excludes compression/migration replacement jobs. This does not defend against malicious same-user processes ignoring native locks, as the contract states.

Optional index mutation remains unimplemented and unapproved in the reviewed production adapter; it is represented as retained. Unknown non-rollout files remain untouched. Unknown or malformed relevant rollout/header inventory is allowed to block when it prevents dependency proof; a generic unrelated cache is not treated as primary ownership evidence. Uncertain outcomes preserve consumed intent and have no automatic retry or whole-store restoration.

Only this report was changed by the independent reviewer. No tests or provider effects were executed during this checkpoint. Parent and implementation owners received findings directly. A final independent follow-up must review the integrated diff and release evidence before any PASS conclusion.

## Integrated follow-up (2026-11-01)

The original five checkpoint items are now implemented in the integrated working tree: provider constants/storage spelling moved to `scoped_profile.rs`; target header and row producer versions are checked on observation and under fences; conservative current-configuration admission is repeated; terminal approval explicitly discloses irreversibility, residuals and logical bytes; and an ignored production-adapter acceptance path uses the real pinned binary for read-only hashing and an actual sandboxed helper. Two additional concrete final-review findings were communicated immediately:

- **SQLite sidecar aliases:** initial writable acquisition only checked the main database. An existing hardlinked WAL/SHM could alias another file. The owner has now added a descriptor-held sidecar guard before writable SQLite, requiring existing WAL and SHM regular single-link files on the root device, rejecting a rollback journal, and checking held physical identities after exclusion and before unlink/commit. Handles outlive SQLite to avoid releasing process-scoped POSIX locks by closing another descriptor early. Negative hardlink/symlink tests were added. This resolves the observed full-adapter alias path; final integrated tests are pending.
- **Known canonical DB paths outside header inventory:** the initial reference proof inspected canonical rollout names in active/archived namespaces but did not account for every other `threads.rollout_path`. A known selected row may point to a custom or external file with a `history_base` dependency on the target. Native source permits DB-selected custom paths (`rollout/src/tests.rs:405`, thread-store selected-path resolver). Ignoring those known rows can damage another session, unlike retaining unobserved historical external copies. Planning and the actual database fence must require every known selected rollout to be covered by the inspected, safe header inventory or conservatively refuse. Resolution pending at this checkpoint.

The updated architecture fitness script retains the domain-storage ban, limits the SQL-string exemption to the fixed private storage module, checks the exact two approved DELETE strings and private `apply` placement, limits descriptor-relative mutation to one fixed `unlinkat` in `validate_and_unlink`, and keeps provider approval minting and eight-tool MCP restrictions. The new test-source filtering matches Rust `cfg(test)` compilation, including whole files and `all(test, unix)` modules. Development dependency relaxation is confined to the Codex provider's application dependency for disposable acceptance. No blanket production mutation or authority waiver was identified. This lexical fitness check supplements source review and compiled tests; it is not a security proof against deliberately obfuscated future code.
